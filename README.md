# AI Health Web Assignment

## 프로젝트 진행 회고 (Day1 ~ Day11)

> Day11 과제: 지금까지의 프로젝트 진행 과정을 팀원들과 되돌아보고, 단계별로 어떻게 진행했는지 정리한 기록 남기기

### 진행 방식에 대한 팀의 선택

기존 프로젝트 의도는 팀원끼리 역할(프론트/백엔드/인프라 등)을 나눠 각자 일부를 맡아 결과물을 구현하는 방식이었지만 저희 조는 **팀원 각자가 기획부터 요구사항 정의, API 설계, 백엔드 구현, 프론트엔드 연동, Docker 인프라 구성까지 전체 사이클을 혼자 완주**하는 방식을 택했습니다.

역할을 나눴다면 더 편했겠지만, 그만큼 "내가 맡은 조각"만 경험하고 끝났을 겁니다. 대신 각자 처음부터 끝까지 부딪혀보면서, 프론트엔드와 백엔드가 실제로 어떻게 맞물리는지, 인프라 구성이 API 설계에 어떤 제약을 주는지를 몸으로 익혔습니다. 그 결과 팀 저장소에는 팀원마다 각자의 완결된 구현이 담긴 브랜치가 쌓였고, 최종적으로는 그중 요구사항 충족도와 안정성이 가장 좋은 브랜치를 팀장님의 코드리뷰를 거쳐 대표 브랜치로 선정해 통합하는 방식으로 진행했습니다.

### 단계별 진행 정리

**1. Team Rule 정의**
커밋 메시지 컨벤션(`Feat`, `Refactor`, `fix:`, `docs:`, `chore:`)과 브랜치 운영 가이드(`Branch_Setting_Guide`)를 초반에 문서화했습니다. Day 단위로 과제가 주어지는 일정에 맞춰, 각자 로컬에서 작업하고 원격에 개인 브랜치를 두는 구조로 팀 규칙을 잡았습니다.

**2. 사용자 요구사항 정의**
초반(Day1~3)에는 주어진 요구사항 문서를 읽고 이해하는 데 집중했다면, 이후로는 각자 담당하는 기능에 대해 직접 요구사항(USR)을 도출하고 구현하고 문서화하는 경험을 쌓았습니다.

**3. API 명세서 작성**
Day별로 설계 문서를 남기며 진행했습니다(예: User API 명세, 환자관리 API 설계, 폐렴예측 API 설계 등). 엔드포인트와 요청/응답 스키마를 문서로 먼저 합의한 뒤 구현에 들어가는 순서를 지켰습니다.

**4. Git & GitHub Branch 전략 구성**
`main`(안정 배포 기준) → `feature`(팀 통합 기준) → 개인 `*_sub*`/`*_dayN` 브랜치 순의 계층 구조를 사용했습니다. PR 병합은 팀장이 GitHub에서 직접 리뷰 후 merge commit 방식으로 처리했고, 팀원들의 병합 요청은 체크포인트 시점에 모아서 처리하는 방식이었습니다.

**5. 프로젝트 세팅**
`uv` 기반 의존성 관리, `pyproject.toml` 구성으로 초기 프로젝트를 세팅했습니다. 이후 AI 예측 기능이 추가되면서 웹 서버(`app`)와 AI 워커(`ai`) 의존성을 분리해 이미지 용량을 최적화했습니다.

**6. API 및 AI 워커 코드 작성 후 Branch 전략을 통한 병합**
각자의 브랜치에서 전체 기능(User API → 환자/진료기록 API → AI 예측 API → 프론트 연동)을 순서대로 구현했습니다. Day7~10 구간에서는 두 명 이상의 팀원이 각자 완성한 브랜치를 팀장이 코드리뷰로 비교해, 요구사항 충족도·테스트 범위·기존 기능 보존 여부를 기준으로 대표 브랜치를 선정하고 나머지 팀원의 개선 아이디어를 반영하는 방식으로 통합했습니다.

**7. 아키텍처 설계 및 적용**
초기에는 FastAPI가 요청을 받아 AI 모델을 동기적으로 직접 호출하는 구조였지만, 응답 지연 문제를 해결하기 위해 Redis 기반 Event-Driven Architecture(작업 큐 + Pub/Sub)로 전환을 설계하고 실제로 적용했습니다. FastAPI는 Redis 큐에 작업을 등록하고 결과를 구독하며, 별도의 AI Worker가 큐에서 작업을 꺼내 예측을 수행하고 결과를 발행하는 구조입니다.

**8. 도커 인프라 관련 파일 작성**
서비스별 `Dockerfile`(FastAPI/AI Worker 분리), `.dockerignore`, `docker-compose.yml`(FastAPI + MySQL + Redis + AI Worker)을 단계적으로 작성했습니다. 컨테이너 기동 시 `alembic upgrade head`가 healthcheck 통과 후 자동 실행되도록 구성해, 새 볼륨에서도 별도 수동 명령 없이 스키마가 준비되도록 했습니다.

**9. AWS 배포**
아직 진행 전 단계입니다(Day12 예정). 현재는 로컬 개발/통합 테스트 기준으로 `docker-compose.yml`을 구성해두었고, 실제 배포 시에는 정적/미디어 파일을 named volume으로 분리하고 모델 파일은 이미지에 포함하지 않는 등 production 전용 구성(`docker-compose.prod.yml`)이 별도로 필요하다는 점을 파악해둔 상태입니다.

**10. QA 진행**
- 동시 요청 중복 생성 방지 테스트 — 같은 예측 요청이 동시에 들어와도 결과가 중복 저장되지 않는지 확인 (완료, 2026-09-07)
- API 응답시간 측정 — Redis 왕복 포함 최초 추론 약 0.87초, 캐시 재사용 시 0.007초로 목표치 3초 이내 충족
- Compose DB 연동 검증 — 회원가입/로그인/`/users/me`를 실제로 호출해 DB 연동 확인
- Alembic 멀티헤드 발견 — 중복된 초기 마이그레이션 파일로 head가 2개가 되는 문제를 QA 과정에서 발견, 별도 PR로 분리 수정
- 전체 테스트 결과 — 로컬에서 Redis까지 붙여 돌렸을 때 46개 중 45개 통과, 나머지 1개는 알려진 동시성 한계로 분류

## Alembic Migration Guide

이 프로젝트는 데이터베이스 마이그레이션을 위해 Alembic을 사용합니다.

### 1. 마이그레이션 파일 생성 (자동 생성)
모델(`app/models/`)이 변경된 경우 다음 명령어를 실행하여 마이그레이션 파일을 생성합니다.
```bash
uv run alembic revision --autogenerate -m "변경 내용 설명"
```

### 2. 데이터베이스에 반영
생성된 마이그레이션을 데이터베이스에 적용하려면 다음 명령어를 실행합니다.
```bash
uv run alembic upgrade head
```

### 3. 이전 상태로 되돌리기 (Rollback)
마지막 마이그레이션을 취소하려면 다음 명령어를 실행합니다.
```bash
uv run alembic downgrade -1
```
