## 잘된 점

1. API 프로세스와 AI 추론 프로세스를 분리해 무거운 모델 의존성이 웹 이미지에 포함되지 않도록 구성했습니다.
2. 예측 요청을 Redis 큐로 넘기고 Worker가 처리하는 비동기 구조를 실제 코드로 구현했습니다.
3. 이미지 해시와 `(record_id, ai_model)` 제약을 통해 같은 입력의 중복 예측을 줄이려는 방향이 명확합니다.
4. Day7부터 Day10까지 작업 브랜치가 순차적으로 이어져 과제 진행 이력을 추적하기 쉽습니다.

## 수정이 필요한 사항

### 병합 전 필수

1. `docker-compose.yml`에서 FastAPI가 사용하는 DB 계정과 MySQL이 생성하는 계정을 일치시켜야 합니다. 현재 `.env.example`의 `DB_USER`를 기준으로 실행하면 인증 실패 가능성이 있습니다.
2. 새 DB에서 컨테이너만 실행해도 스키마가 준비되도록 FastAPI 시작 전에 `alembic upgrade head`를 수행해야 합니다.
3. `PREDICTION_TIMEOUT_SECONDS=60`은 모든 API를 3초 안에 응답해야 한다는 NFR과 충돌합니다.
4. 예측 권한이 부서 값만으로 결정되어 승인 대기 상태 사용자도 호출할 수 있으므로, 프로젝트 공통 승인 사용자 의존성을 사용해야 합니다.
5. 요구사항은 예측 결과 목록 조회를 요청하지만 현재 조회 API는 단일 객체를 반환합니다.

### 품질 개선

1. Day10 전용 API·서비스·Worker 테스트가 없어 Redis 장애, timeout, 캐시 적중, 동시 요청을 자동 검증하지 못합니다.
2. 파일 확장자나 `image/*` 여부만 믿지 말고 실제 이미지 디코딩, 업로드 크기 상한, 저장 경로 검증이 필요합니다.
3. 동기 파일 I/O가 비동기 요청 처리 경로에 있으므로 큰 파일에서 이벤트 루프를 막을 수 있습니다.
4. 단일 전역 결과 채널보다 요청별 채널을 사용하면 다른 요청의 결과를 반복해서 검사하는 비용과 메시지 혼선을 줄일 수 있습니다.

## 검증 결과

- Alembic head: 1개
- 사용자 API 테스트: 3개 통과
- Day10 예측 API/Redis Worker 전용 테스트: 없음
- Compose 설정: 구문 검증은 통과했으나 `.env.example` 계정 조합으로 실제 MySQL 연결이 보장되지 않음
