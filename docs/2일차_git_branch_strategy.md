# Git & GitHub 브랜치 전략

## 1. Git Flow

### 정의
전통적인 브랜칭 전략으로, 여러 종류의 브랜치를 나누어 구조화된 버전 관리를 진행합니다. 단계별 릴리스 프로세스를 통해 안정적인 배포를 보장합니다.

### 브랜치 구조
- **master**: 프로덕션에 배포 가능한 안정적인 코드
- **develop**: 다음 릴리즈를 위한 통합 브랜치
- **feature**: 개별 기능 개발 브랜치
- **release**: 릴리즈 준비 및 테스트 브랜치
- **hotfix**: 프로덕션 긴급 버그 수정 브랜치

### 워크플로우
1. feature 브랜치에서 기능 개발
2. develop 브랜치로 병합
3. release 브랜치에서 릴리즈 준비
4. master 브랜치로 배포
5. 필요시 master에서 hotfix 분기

### 특징
- 복잡하지만 체계적인 버전 관리
- 대규모 팀이나 엔터프라이즈 제품에 적합
- 배포 위험성 감소

---

## 2. GitHub Flow

### 정의
단순한 브랜칭 전략으로, 기본 브랜치(master)와 기능 브랜치(feature)만 사용합니다. 빠른 반복 개발과 지속적 배포에 최적화되어 있습니다.

### 브랜치 구조
- **master**: 배포 가능한 안정적인 코드
- **feature**: 개별 기능 개발 브랜치 (필요시만 생성)

### 워크플로우
1. master에서 feature 브랜치 생성
2. 기능 개발 완료 후 Pull Request 생성
3. 코드 리뷰 진행
4. 리뷰 완료 후 master에 병합
5. 즉시 배포 가능

### 특징
- 간단하고 직관적
- 스타트업이나 중소 팀에 적합
- 빠른 반복과 지속적 배포 가능
- 강력한 테스트 체계 필요

---

## 3. Git Flow vs GitHub Flow 비교

| 항목 | Git Flow | GitHub Flow |
|------|----------|------------|
| **복잡도** | 높음 (5개 브랜치) | 낮음 (2개 브랜치) |
| **학습곡선** | 가파름 | 완만함 |
| **배포 전략** | 단계별 배포 | 지속적 배포 (CD) |
| **릴리즈 관리** | 체계적 버전 관리 | 유연한 버전 관리 |
| **팀 규모** | 대규모 팀 | 소규모~중규모 팀 |
| **프로젝트 유형** | 엔터프라이즈, 대규모 | 스타트업, 빠른 반복 개발 |
| **배포 위험도** | 낮음 | 중간 (테스트 의존도 높음) |
| **코드 리뷰** | release/hotfix 단계 | Pull Request 기반 |

---

## 4. 우리 팀이 선택한 전략

### 선택한 전략: GitHub Flow

### 선택 이유:

1. **팀 규모가 적음** (3명)
   - Git Flow는 대규모 팀에 맞게 설계된 전략
   - GitHub Flow는 소규모 팀에 최적화되어 있음

2. **학습 곡선이 완만함**
   - GitHub Flow는 브랜치 2개만 사용 (master + feature)
   - 팀원들이 쉽게 이해하고 따를 수 있음

3. **빠른 반복 개발이 필요함**
   - 학교 프로젝트는 정해진 릴리즈 주기가 없음
   - 주기적으로 업데이트하고 배포하기에 적합

4. **복잡한 릴리즈 관리가 불필요함**
   - release, hotfix 브랜치 관리의 오버헤드 제거
   - Pull Request만으로 코드 리뷰 가능

5. **더 빠른 개발 속도**
   - develop 브랜치 병합 단계 없음
   - feature → master로 바로 병합 (테스트 거친 후)

## 5. Git 기본 명령어

### 1단계: 기본 초급 명령어

#### 1-1. `git init` (로컬 저장소 초기화)
새로운 Git 저장소를 시작합니다. 폴더에 `.git` 폴더를 생성하여 버전 관리를 시작합니다.
```bash
git init
```

#### 1-2. `git branch` (브랜치 목록 확인/생성/삭제)
브랜치를 생성, 조회, 삭제합니다.
```bash
git branch              # 현재 브랜치 목록 조회
git branch <브랜치명>   # 새 브랜치 생성
git branch -d <브랜치명> # 브랜치 삭제
```

#### 1-3. `git checkout` (브랜치 이동/특정 커밋 해시로 이동)
브랜치를 전환하거나 이전 커밋으로 돌아갑니다.
```bash
git checkout <브랜치명>  # 브랜치 이동
git checkout <커밋해시>  # 특정 커밋으로 이동
```

#### 1-4. `git switch` (브랜치 이동 전용)
`checkout`보다 명확하게 브랜치 이동만 담당합니다. (최신 Git 권장)
```bash
git switch <브랜치명>
```

#### 1-5. `git status` (현재 상태 확인)
현재 브랜치, 커밋 상태, 변경된 파일 목록을 확인합니다.
```bash
git status
```

#### 1-6. `git add` (커밋할 파일을 Stage 상태로 추가)
변경된 파일을 커밋 대기 상태로 만듭니다.
```bash
git add <파일명>     # 특정 파일 추가
git add .            # 모든 변경 파일 추가
```

#### 1-7. `git commit` (변경 사항 기록/저장)
Stage에 있는 파일들을 커밋하여 버전 이력으로 저장합니다.
```bash
git commit -m "커밋 메시지"
```

#### 1-8. `git remote` (원격 저장소 관리)
원격 저장소(예: GitHub)를 등록하고 관리합니다.
```bash
git remote add origin <URL>  # 원격 저장소 추가
git remote -v                # 원격 저장소 확인
```

#### 1-9. `git push` (원격 저장소에 업로드)
로컬 커밋을 원격 저장소에 올립니다.
```bash
git push origin <브랜치명>
```

#### 1-10. `git log` (전체 변경 이력 확인)
커밋 이력을 시간순으로 조회합니다.
```bash
git log              # 전체 커밋 이력
git log --oneline    # 간단한 형식
```

#### 1-11. 전체 작업 흐름 요약
```bash
git init              # 저장소 시작
git branch feature    # 브랜치 생성
git checkout feature  # 브랜치 이동
# 파일 수정 작업
git add .            # 변경 파일 추가
git commit -m "msg"  # 커밋
git push origin feature # 원격에 업로드
```

---

### 2단계: 작업 내역 관리를 위한 중급 명령어

#### 2-1. `git merge` (작업 내역 합치기)
한 브랜치의 변경사항을 다른 브랜치에 병합합니다.
```bash
git checkout main
git merge <브랜치명>  # 현재 브랜치에 병합
```

#### 2-2. `git revert` (커밋 이력은 보존하고 작업 내역 되돌리기)
특정 커밋의 변경사항을 취소하는 **새로운 커밋**을 만듭니다. 이력이 남습니다.
```bash
git revert <커밋해시>
```

#### 2-3. `git reset` (커밋 이력 삭제)
커밋을 완전히 삭제합니다. 이력에서 제거됩니다. (주의: 협업시 위험)
```bash
git reset --hard <커밋해시>  # 강제 리셋
git reset --soft <커밋해시>  # 커밋만 취소
```

#### 2-4. `git rebase` (커밋 내역 정리 - Git 시스템 의존)
여러 커밋을 하나로 정리하거나 순서를 변경합니다. 자동으로 진행됩니다.
```bash
git rebase <브랜치명>
```

#### 2-5. `Interactive Rebase` (커밋 내역 정리 - 사용자 개입)
사용자가 각 커밋마다 선택하여 커밋을 정리합니다. (더 정밀한 제어 가능)
```bash
git rebase -i <커밋해시>
```

#### 2-6. `git cherry-pick` (커밋 가져오기)
특정 브랜치의 특정 커밋만 현재 브랜치에 가져옵니다.
```bash
git cherry-pick <커밋해시>
```

## 6. Conflict(충돌) 해결방법

### 충돌이 발생하는 상황

`Pull`, `Rebase`, `Merge` 등의 명령어를 사용할 때, **동일한 파일의 같은 부분을 다른 사람이 수정했을 경우** 충돌이 발생합니다.

### 예시 상황

```bash
# 원격 develop 브랜치 (다른 사람이 수정해서 push)
A --- B --- C (origin/develop)
           ↑ 새로운 커밋 C (같은 파일 수정)

# 내 feature 브랜치 (rebase 전)
A --- B --- L1 --- L2 (feature/login)
                   ↑ 내 작업 커밋 (같은 파일 수정)
```

**상황**: `git pull --rebase origin develop` 실행 시 충돌 발생!

### 충돌 메시지 읽기

충돌이 난 파일을 열면 다음과 같이 표시됩니다:

```bash
# A파일
...
<<<<<<< HEAD
print("hello")  ← develop 브랜치의 변경사항
=======
print("hi")     ← feature/login 브랜치의 변경사항
>>>>>>> L1
...
```

### 충돌 해결 단계

#### 1단계: 충돌 부분 확인 및 수정
- `<<<<<<< HEAD ~ =====` : 원격 저장소의 변경사항
- `===== ~ >>>>>>> L1` : 내 로컬 브랜치의 변경사항

**둘 중 맞는 코드만 남기고, 충돌 표시 라인들은 모두 삭제합니다:**

```bash
# 수정 후
...
print("hello")  ← 선택한 코드만 남김
...
```

#### 2단계: 수정된 파일 스테이징
```bash
git add 수정한파일경로
```

#### 3단계: Rebase 계속 진행
```bash
git rebase --continue
```

### 충돌 해결의 핵심 💡

1. **팀원과 소통하기**: 충돌난 부분을 확인하고 해당 커밋을 작성한 팀원과 대화하기
2. **코드 흐름 파악하기**: 어떤 코드가 맞는지 신중하게 판단하기
3. **확신 없으면 abort하기**: 
   ```bash
   git rebase --abort  # rebase 이전 상태로 되돌리기
   ```

## 7. 팀 협업 시 주의사항

- **브랜치 명명 규칙 통일**: `feature/기능명` 형식 일관되게 사용
- **항상 PR을 통해 Merge**: 직접 merge하지 말기, 코드 리뷰 필수
- **주기적으로 동기화**: 충돌을 줄이기 위해 주기적으로 develop 브랜치 pull받기
- **작업 완료 후 브랜치 삭제**: GitHub에서 브랜치 정리하기
- **커밋 메시지 규칙 지키기**: 팀 컨벤션에 따라 작성하기
