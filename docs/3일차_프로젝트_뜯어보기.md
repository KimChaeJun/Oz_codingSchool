# 3일차 프로젝트 템플릿 뜯어보기

## 1. 프로젝트 구조와 전체 흐름

이 프로젝트는 FastAPI 애플리케이션을 역할별 계층으로 나누고, SQLAlchemy의 비동기 세션으로 MySQL에 접근하며, Alembic으로 데이터베이스 스키마 변경 이력을 관리하도록 구성되어 있다.

```text
HTTP 요청
  ↓
apis (라우팅·HTTP 입출력)
  ↓
schemas (요청·응답 데이터 검증)
  ↓
services (비즈니스 규칙·트랜잭션 흐름)
  ↓
repositories (SQLAlchemy 조회·저장)
  ↓
models + core/db (ORM 메타데이터·세션·DB 연결)
  ↓
MySQL
```

현재 저장소는 과제 안내의 예시 구조와 일부 차이가 있다.

- 정적 파일은 `app/static/`이 아니라 프로젝트 루트의 `static/`에 있다.
- HTML 조각은 `app/templates/`가 아니라 `static/templates/`에 있다.
- 업로드 파일용 `media/`와 정적 파일용 `static/`은 `app/main.py`가 프로젝트 루트를 기준으로 사용한다.
- `app/models/`, `app/repositories/`, `app/schemas/`, `app/services/`에는 현재 `__init__.py`만 있으며 이후 기능 구현 시 파일을 추가한다.
- `app/Dockerfile`은 현재 비어 있으므로 Docker 이미지 실행이 필요하면 빌드 단계를 추가해야 한다.

## 2. 디렉터리별 역할과 작성할 내용

### `app/core/`

애플리케이션 전체가 공통으로 사용하는 기반 설정을 둔다. 특정 기능이나 HTTP 요청에 종속되지 않는 코드가 들어간다.

현재 파일과 역할은 다음과 같다.

- `config.py`: `.env`에서 환경 변수를 읽고 설정 객체를 만든다.
- `db/databases.py`: DB URL, 비동기 엔진, 세션 팩토리, SQLAlchemy `Base`, 세션 의존성을 정의한다.
- `db/models.py`: UUID, 생성·수정 시각, 소프트 삭제처럼 여러 ORM 모델에서 재사용할 mixin을 정의한다.

추가로 작성할 수 있는 내용은 인증 설정, 로깅, 공통 예외, 보안 유틸리티 등이다. 비밀번호나 DB 접속 정보처럼 환경마다 달라지는 값은 코드에 직접 작성하지 않고 설정 객체를 통해 주입한다.

### `app/models/`

데이터베이스 테이블과 대응하는 SQLAlchemy ORM 모델을 작성한다. 일반적으로 테이블 하나당 파일 하나를 사용한다.

모델에는 다음 내용을 작성한다.

- `__tablename__`
- 기본 키와 일반 컬럼
- `ForeignKey`, `UniqueConstraint`, 인덱스 등의 DB 제약조건
- `relationship()`을 이용한 모델 간 관계
- 필요한 경우 공통 timestamp·soft-delete mixin

`app/models/__init__.py`에서 모든 모델 클래스를 import해야 Alembic이 `Base.metadata`를 통해 전체 테이블을 발견할 수 있다.

### `app/repositories/`

DB 접근 코드를 캡슐화한다. SQLAlchemy의 `select()`, `insert()`, `update()`, `delete()` 및 `AsyncSession` 사용 코드를 이 계층에 모은다.

예를 들어 `UserRepository`에는 다음 기능을 작성할 수 있다.

- 이메일로 회원 조회
- 회원 ID로 단건 조회
- 회원 목록 조회
- 회원 객체 추가 및 삭제

HTTP 상태 코드나 비즈니스 정책은 repository가 결정하지 않는다. repository는 데이터 저장과 조회에 집중하고, 조회 결과를 service에 반환한다.

### `app/schemas/`

FastAPI가 요청과 응답을 검증·직렬화할 때 사용하는 Pydantic 모델을 작성한다. DB 테이블 구조를 그대로 노출하지 않고 API 목적에 맞게 구분한다.

예시는 다음과 같다.

- `UserCreate`: 회원 생성 요청
- `UserUpdate`: 회원 부분 수정 요청
- `UserResponse`: 비밀번호를 제외한 회원 응답

문자열 길이, 이메일 형식, 숫자 범위 등 입력값 자체의 형식은 schema에서 검증한다. 이메일 중복처럼 DB 조회가 필요한 규칙은 service에서 처리한다.

### `app/services/`

애플리케이션의 비즈니스 규칙과 작업 순서를 작성한다. API와 repository 사이에서 여러 DB 작업을 조합하고 트랜잭션의 성공·실패를 관리한다.

회원가입을 예로 들면 다음 순서가 service의 책임이다.

1. repository를 통해 이메일과 전화번호 중복 확인
2. 비밀번호 해시 생성
3. ORM 객체 생성 및 저장
4. 트랜잭션 commit
5. 필요한 응답 객체 반환

이 계층을 두면 동일한 규칙을 HTTP API뿐 아니라 배치 작업이나 테스트에서도 재사용할 수 있다.

### `app/apis/`

`APIRouter`를 사용해 endpoint와 HTTP method를 정의한다. path/query parameter와 request body를 받고 service를 호출한 뒤 response schema로 반환한다.

이 계층의 주된 책임은 다음과 같다.

- URL과 HTTP method 선언
- `Depends()`를 이용한 DB 세션·인증 정보 주입
- 요청·응답 schema 지정
- 비즈니스 예외를 적절한 HTTP 상태 코드로 변환

복잡한 SQL이나 비밀번호 처리 같은 비즈니스 로직을 endpoint 함수 안에 직접 작성하지 않는다.

## 3. 주요 파일의 역할

### `app/main.py`

FastAPI 애플리케이션의 진입점이다.

현재 다음 작업을 수행한다.

- `FastAPI()` 인스턴스 생성
- `app.include_router(router)`로 API 라우터 등록
- `/static`, `/media` 경로 마운트
- `/healthcheck` 상태 확인 endpoint 제공
- `/`에서 SPA의 `static/index.html` 반환
- 등록된 API나 정적 파일이 아닌 경로를 SPA로 보내는 catch-all route 제공

catch-all route는 다른 구체적인 route보다 뒤에 선언해야 한다. 먼저 선언하면 정상 API 요청까지 가로챌 수 있다. 기능이 늘어나면 각 도메인의 router를 import해 `include_router()`로 조합한다.

### `app/core/config.py`

`pydantic-settings`의 `BaseSettings`를 사용하여 다음 DB 환경 변수를 읽는다.

- `DB_USER`
- `DB_PASSWORD`
- `DB_HOST`
- `DB_PORT`
- `DB_NAME`

`model_config.env_file`이 `.env`로 지정되어 있어 로컬 개발자는 프로젝트 루트에 `.env`를 직접 만들어야 한다. `.env`에는 비밀정보가 포함될 수 있으므로 Git에 커밋하지 않는다.

### `pyproject.toml`

Python 프로젝트의 표준 설정 파일이다. 현재 프로젝트 이름, 버전, 지원 Python 버전과 런타임 의존성을 선언한다.

주요 의존성은 다음과 같다.

- `fastapi[standard]`: API 서버 및 개발 도구
- `sqlalchemy[asyncio]`: 비동기 ORM
- `asyncmy`: MySQL 비동기 드라이버
- `alembic`: DB 스키마 마이그레이션
- `pydantic-settings`: 환경 변수 기반 설정
- `cryptography`: MySQL 인증 등 암호화 기능 지원

의존성을 변경할 때는 파일을 직접 고치기보다 `uv add 패키지명` 또는 `uv remove 패키지명`을 사용하면 `pyproject.toml`과 lock 파일을 함께 관리할 수 있다.

### `uv.lock`

직접 의존성과 하위 의존성의 정확한 버전을 고정하는 파일이다. 팀원이 `uv sync`를 실행했을 때 동일한 패키지 조합을 설치하게 해 재현 가능한 개발 환경을 만든다.

`pyproject.toml`이 "어떤 패키지가 필요한가"를 선언한다면, `uv.lock`은 "실제로 어떤 버전 조합을 설치할 것인가"를 기록한다. 애플리케이션 코드처럼 Git에 함께 커밋하며 수동으로 편집하지 않는다.

## 4. 데이터베이스 연결 설정

### 환경 변수

로컬에서 FastAPI와 MySQL을 모두 직접 실행한다면 다음과 같은 `.env`를 사용할 수 있다. 실제 비밀번호로 바꾸되 저장소에는 올리지 않는다.

```dotenv
DB_USER=app_user
DB_PASSWORD=change_me
DB_HOST=localhost
DB_PORT=3306
DB_NAME=ai_health
```

Docker Compose 네트워크 안에서 FastAPI 컨테이너가 MySQL 컨테이너에 접속한다면 `DB_HOST`는 서비스 이름인 `mysql`이어야 한다.

### 비동기 엔진과 세션

`app/core/db/databases.py`는 설정값으로 다음 형식의 URL을 만든다.

```text
mysql+asyncmy://사용자:비밀번호@호스트:포트/데이터베이스명
```

그리고 다음 객체를 준비한다.

- `async_engine`: DB 연결 풀과 SQL 실행을 관리하는 비동기 엔진
- `AsyncSessionLocal`: 요청마다 `AsyncSession`을 생성하는 팩토리
- `Base`: 모든 ORM 모델이 상속할 선언형 base
- `async_get_db()`: FastAPI의 `Depends()`에서 사용할 세션 generator

API에서의 사용 예시는 다음과 같다.

```python
from typing import Annotated

from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession

from app.core.db.databases import async_get_db

DBSession = Annotated[AsyncSession, Depends(async_get_db)]


async def example_endpoint(db: DBSession):
    ...
```

`async with` 블록이 끝나면 세션이 닫히므로 요청마다 연결 자원을 안전하게 반환할 수 있다. 데이터 변경 시에는 service에서 `commit()`을 수행하고 오류가 발생하면 `rollback()`한다.

## 5. SQLAlchemy 모델과 Alembic 마이그레이션

### 모델 작성

SQLAlchemy 2.x 스타일에서는 `Mapped`와 `mapped_column()`으로 Python 타입과 DB 컬럼을 함께 선언한다.

```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

from app.core.db.databases import Base


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, nullable=False)
```

모델을 만든 뒤 `app/models/__init__.py`에서 import한다.

```python
from app.models.user import User

__all__ = ["User"]
```

현재 `alembic/env.py`가 `from app import models`를 실행하고 `Base.metadata`를 `target_metadata`로 사용하므로 이 import 과정이 빠지면 autogenerate가 테이블을 감지하지 못한다.

### 마이그레이션 생성과 적용

1. MySQL을 실행하고 `.env`의 접속 정보를 확인한다.
2. ORM 모델을 작성하고 `app/models/__init__.py`에 등록한다.
3. 모델과 현재 DB schema의 차이를 바탕으로 migration을 생성한다.

```bash
uv run alembic revision --autogenerate -m "헬스케어 테이블 생성"
```

4. 생성된 `alembic/versions/*.py`의 `upgrade()`와 `downgrade()`를 검토한다. autogenerate 결과는 초안이므로 FK 삭제 정책, enum, nullable, unique 제약조건이 의도와 같은지 반드시 확인한다.
5. 최신 migration까지 적용한다.

```bash
uv run alembic upgrade head
```

6. 적용 상태를 확인한다.

```bash
uv run alembic current
uv run alembic history
```

7. 마지막 migration을 되돌려야 할 때는 다음을 실행한다.

```bash
uv run alembic downgrade -1
```

migration 파일은 DB 변경 이력이므로 모델 파일과 함께 Git에 커밋한다. 팀원이 임의로 수정한 DB schema가 아니라 migration을 실행해 동일한 schema를 재현할 수 있어야 한다.

## 6. API 구현 흐름

회원 생성 API를 계층별로 나누면 다음과 같다.

1. `apis/users.py`가 `POST /users` 요청을 수신한다.
2. `schemas/user.py`의 `UserCreate`가 이메일, 비밀번호, 이름 등의 형식을 검증한다.
3. API가 `Depends(async_get_db)`로 요청 전용 DB 세션을 받는다.
4. `services/user.py`가 이메일 중복 확인과 비밀번호 해시 같은 비즈니스 규칙을 수행한다.
5. `repositories/user.py`가 SQLAlchemy query를 실행하고 `models/user.py`의 `User` 객체를 저장한다.
6. service가 transaction을 commit한다. 실패하면 rollback하고 적절한 애플리케이션 예외를 발생시킨다.
7. API가 `UserResponse` schema로 안전한 필드만 반환한다. `hashed_password` 같은 내부 필드는 응답에서 제외한다.

각 계층을 분리하면 다음과 같은 장점이 있다.

- API 함수가 짧아지고 HTTP 처리에 집중한다.
- DB query를 repository 단위로 테스트할 수 있다.
- 비즈니스 규칙을 여러 endpoint에서 재사용할 수 있다.
- ORM 모델과 외부 응답 형식을 분리해 민감정보 노출을 방지한다.
