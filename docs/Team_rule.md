## 2조 Team Rules

### 1. 코어 타임
수업 종료 후 매일 15:20~16시, Zep에 모여서 진행하기


### 2. 쿠션어 사용하기
상대방을 배려해서 무슨일이 있어도 감정은 절제하고, 부드러운 언어로 대화하기
화나면 잠깐 바람쐬고오기

### 3. 적극적인 회의 참여
팀 프로젝트 과제 수행중 필요한 회의에서 마이크는 항상키고, 눈치보지않고 적극적인 의사표명하기

## 4. Git & Github Rules

- 작업은 개인 브랜치에서 진행하기
- 작업 전 `main` 브랜치의 최신 내용을 `pull`하기
- 작업 완료 후 원격 저장소에 `push`하기
- 다른 사람의 작업 내용을 임의로 수정하거나 삭제하지 않기
- 충돌이 발생하면 팀원들과 공유하고 함께 해결하기

## 5. 커밋 메시지 작성 규칙

커밋 메시지는 **어떤 작업을 했는지 다른 팀원이 바로 이해할 수 있도록 작성**합니다.

기본 형식은 다음과 같이 통일합니다.

```text
타입: 작업 내용
```

예시:

```text
feat: 로그인 페이지 구현
fix: 로그인 버튼 오류 수정
style: 메인 페이지 CSS 수정
docs: README 사용 방법 추가
```

### 1. 커밋 타입

| 타입         | 사용 상황                  | 예시                       |
| ---------- | ---------------------- | ------------------------ |
| `feat`     | 새로운 기능을 추가한 경우         | `feat: 회원가입 기능 구현`       |
| `fix`      | 오류나 버그를 수정한 경우         | `fix: 로그인 실패 오류 수정`      |
| `style`    | CSS, 디자인, UI 등을 수정한 경우 | `style: 헤더 디자인 수정`       |
| `refactor` | 기능 변화 없이 코드를 정리한 경우    | `refactor: 로그인 코드 구조 정리` |
| `docs`     | README 등 문서를 수정한 경우    | `docs: 프로젝트 실행 방법 추가`    |
| `chore`    | 설정, 패키지, 환경 관련 작업      | `chore: axios 패키지 설치`    |
| `test`     | 테스트 코드를 추가하거나 수정한 경우   | `test: 로그인 API 테스트 추가`   |

---

### 2. 커밋 메시지는 한국어로 작성

팀원들이 내용을 빠르게 확인할 수 있도록 작업 내용은 한국어로 작성합니다.

```text
feat: 마이페이지 구현
fix: 회원가입 시 이메일 검증 오류 수정
```

커밋 타입은 영어로 통일합니다.

---

### 3. 한 커밋에는 하나의 작업만 포함

가능하면 서로 다른 작업을 하나의 커밋에 한꺼번에 넣지 않습니다.

좋은 예:

```text
feat: 로그인 UI 구현
feat: 로그인 API 연결
fix: 로그인 실패 메시지 수정
```

좋지 않은 예:

```text
feat: 로그인 구현하고 CSS 수정하고 회원가입 오류 수정
```

작업을 나누어 커밋하면 나중에 어떤 부분에서 문제가 발생했는지 찾기 쉬워집니다.

---

### 4. 작업 내용을 알아볼 수 있게 작성

다음과 같이 의미를 알기 어려운 커밋 메시지는 사용하지 않습니다.

```text
수정
수정함
작업
완료
최종
최종수정
진짜최종
update
test
```

대신 무엇을 수정했는지 구체적으로 작성합니다.

```text
fix: 로그인 버튼 클릭 오류 수정
style: 메인 페이지 버튼 간격 수정
feat: 게시글 삭제 기능 추가
```

---

### 5. 너무 긴 메시지는 작성하지 않기

커밋 메시지는 한 줄로 간단하게 작성합니다.

```text
feat: 게시글 작성 기능 구현
```

다음처럼 지나치게 자세하게 작성할 필요는 없습니다.

```text
feat: 게시글 작성 페이지에서 제목과 내용을 입력하고 서버 API로 전송하는 기능을 구현함
```

자세한 설명이 필요한 경우 Pull Request에서 작성합니다.

## 커밋 예시

### 새로운 기능

```bash
git commit -m "feat: 로그인 기능 구현"
```

```bash
git commit -m "feat: 게시글 작성 기능 추가"
```

### 버그 수정

```bash
git commit -m "fix: 로그인 실패 오류 수정"
```

```bash
git commit -m "fix: 게시글 삭제 시 발생하는 오류 수정"
```

### 디자인 수정

```bash
git commit -m "style: 로그인 페이지 디자인 수정"
```

```bash
git commit -m "style: 모바일 화면 레이아웃 수정"
```

### 코드 정리

```bash
git commit -m "refactor: 로그인 API 코드 분리"
```

### 문서 수정

```bash
git commit -m "docs: README 실행 방법 추가"
```

### 프로젝트 설정

```bash
git commit -m "chore: 개발 환경 설정 추가"
```

## 팀 커밋 규칙 요약

```text
1. 형식은 "타입: 작업 내용"으로 작성한다.
2. 타입은 영어, 작업 내용은 한국어로 작성한다.
3. 한 커밋에는 가능한 하나의 작업만 포함한다.
4. "수정", "최종", "작업"처럼 의미 없는 메시지는 사용하지 않는다.
5. 다른 팀원이 봤을 때 무엇을 했는지 이해할 수 있게 작성한다.
```

### 가장 자주 사용하는 타입

처음에는 아래 4개만 기억해도 충분합니다.

```text
feat     새로운 기능
fix      버그 수정
style    디자인/CSS 수정
docs     문서 수정
```

예를 들어 로그인 페이지를 만들었다면:

```bash
git add .
git commit -m "feat: 로그인 페이지 구현"
```

로그인 버튼 오류를 고쳤다면:

```bash
git add .
git commit -m "fix: 로그인 버튼 오류 수정"
```

> **핵심:** 커밋 메시지만 봐도 "이 사람이 무엇을 변경했는지" 알 수 있게 작성합니다.
