# 9일차 - 동시성 문제 해결을 위한 아키텍처 설계

## 학습 배경

지금 프로젝트의 AI 폐렴 예측 API(`prediction_service.py`)는 요청이 동시에 여러 개 들어오면 중복 데이터가 생길 수 있는 구조임. 이 문제를 FastAPI + Redis 기반 Event-Driven Architecture(EDA)로 어떻게 해결할 수 있는지 공부하고, 실제 적용 가능한 설계를 정리함.

---

## 1. 동시성 문제의 원인 `[실제 코드 근거]`

**비유로 먼저 이해**

카페에 손님 두 명이 동시에 "아메리카노 있어요?" 하고 물어봄. 둘 다 "없음" 확인하고, 둘 다 새로 내림. 결과: 아메리카노 2잔 생김. 우리 프로젝트도 똑같은 일이 벌어짐.

**실제 코드에서 일어나는 일**

`app/services/prediction_service.py`에서 예측 요청 들어오면:

1. "이미 예측 결과 있음?" DB 조회 (`get_by_record_and_model`)
2. 없으면 → AI 모델 돌려서 새로 예측 (`predict`)
3. 결과 DB에 저장 (`db.add` → `db.commit`)

문제는 2~3단계 사이임. 같은 진료기록에 예측 요청이 거의 동시에 두 번 들어오면, 둘 다 1단계에서 "없음" 확인하고, 둘 다 무거운 추론 돌리고, 둘 다 DB에 저장함. → 중복 결과 쌓임.

지금은 DB에 "같은 조합(`record_id` + `ai_model`) 하나만 허용" 안전장치(UniqueConstraint)도 없어서, 코드 순서 꼬이면 그대로 중복 생김. (관련: TODO.md의 UniqueConstraint 항목)

**덤으로 생기는 문제**

AI 추론은 시간 걸리는 작업인데, API가 요청 받은 자리에서 `run_in_threadpool`로 돌리고 그 자리에서 기다림. 손님이 커피 다 내려질 때까지 카운터 앞에서 기다리는 것과 같음 — 다른 손님 주문 못 받음(동시 처리량 저하).

**현재 구현 상태 요약** `[실제 코드 근거]`

- 실제 엔드포인트: `POST /api/v1/medical-records/{record_id}/predictions`
- 결과 저장 테이블: `ai_analysis_results`
- 응답 방식: **완전히 동기식**. 요청이 들어온 그 자리에서 추론까지 끝내고 결과를 바로 반환함. 새로 예측했으면 `201 Created`, 기존 캐시 결과를 재사용했으면 `200 OK`로 응답 코드만 바뀜(`prediction_apis.py`의 `response.status_code = status.HTTP_200_OK` 분기)
- 즉 지금은 "즉시 처리 + 즉시 응답" 구조이고, 아래 2번부터 나오는 EDA(비동기 큐잉) 방식은 전부 **아직 구현되지 않은 제안 설계**임

## 2. Event-Driven Architecture 개념 `[학습·설계]`

**비유로 먼저 이해**

잘 되는 카페는 손님이 주문하면 "주문서"만 받아서 주방에 넘기고, 바로 다음 손님 받음. 커피 다 되면 주방/진동벨이 알려줌. 손님은 카운터 앞에서 안 기다림. 이게 EDA임.

**공식 정의로 정리** (Microsoft Azure, IBM 자료 참고)

EDA는 event producer(생성자), event consumer(소비자), event channel/broker(전달 통로)로 구성됨. 핵심은 **producer가 어떤 consumer가 듣고 있는지 모른 채로 이벤트를 던진다**는 것 — 이게 "decoupling(결합 제거)"임. 전통적인 요청-응답 모델은 A가 B를 직접 호출하고 응답 기다리는데, EDA는 A가 "이벤트 발생했다"고 알리기만 하고 끝남.

**용어 정리**

| 용어 | 카페 비유 | 우리 프로젝트 |
|---|---|---|
| Producer | 주문 받는 사람 | FastAPI |
| Event | 주문서 한 장 | "이 X-ray 이미지 예측해줘" |
| Broker/Queue | 주문서 쌓아두는 곳 | Redis |
| Consumer | 주문서 가져다 처리하는 사람 | AI Worker |

---

## 3. FastAPI의 역할

**현재 구현** `[실제 코드 근거]`

지금 `prediction_apis.py` + `prediction_service.py`는 "요청 검증 + 추론 실행 + DB 저장 + 응답 반환"을 FastAPI 프로세스 하나가 전부 동기로 처리함. `POST /api/v1/medical-records/{record_id}/predictions` 요청을 받으면 그 자리에서 `predict()`까지 끝내고 `201`/`200`으로 바로 응답함. Producer/Consumer 분리가 전혀 없는 상태.

**EDA 적용 후 제안 설계** `[학습·설계]`

EDA로 바꾸면 FastAPI는 **Producer이자 API 게이트웨이** 역할만 하게 됨:

- 요청 받고 유효성 검사(진료기록 존재 여부, X-ray 이미지 있는지 등)
- Redis에 "이 작업 해줘" 이벤트만 등록(enqueue)
- 무거운 추론은 절대 직접 안 함 — 등록만 하고 바로 손 뗌
- 클라이언트한테 `202 Accepted` + `task_id` 즉시 응답 (지금의 `201`/`200` 즉시 응답 방식을 대체하는 제안)
- 나중에 상태 물어볼 수 있는 조회 API도 따로 제공 (지금은 존재하지 않음, 신규 제안)

## 4. Redis의 역할 `[학습·설계]`

Redis는 FastAPI(producer)와 AI Worker(consumer) 사이를 이어주는 **중개소** 역할임. 두 가지 쓰임새가 있음:

- **메시지 브로커(broker)**: 작업 요청을 큐에 쌓아두고 워커가 가져가게 함
- **결과 저장소(result backend)**: 작업 상태/결과를 저장해서 나중에 조회 가능하게 함

Redis는 메모리 중심(in-memory) 저장소라 빠르지만, RDB 스냅샷이나 AOF 로그 같은 설정을 켜면 디스크에 영속화도 가능함 — "메모리에만 있고 껐다 켜면 사라지는 저장소"로 단정하면 안 됨.

"작업 큐"로 쓰는 방식은 크게 두 가지로 나뉨: (1) Redis Streams를 직접 다루는 방식, (2) Celery라는 프레임워크의 브로커로 Redis를 붙이는 방식. 처리 속도와 재시도 보장 수준 사이에 트레이드오프가 있다는 건 과제 지정 참고자료에는 없는 내용이라, **추가 조사 자료의 설계 관점**으로만 참고함(확정된 벤치마크가 아니라 개인 블로그의 일반론임 — 아래 참고자료 목록의 markaicode.com 항목).

## 5. Redis 작업 대기열 / Streams 구조 `[학습·설계]`

**Streams 방식 — 원문(oneuptime.com) 그대로의 구조**

oneuptime.com 글이 실제로 설명하는 건 **FastAPI 프로세스 내부에서 `asyncio.create_task`로 컨슈머를 띄우는 방식**임. 별도 워커 프로세스 없이, 하나의 FastAPI 애플리케이션 안에서 producer(엔드포인트)와 consumer(백그라운드 태스크)가 같이 도는 구조:

- `XADD`로 이벤트 발행 (예: `{record_id: 5, image_path: "..."}`)
- Consumer group이 `XREADGROUP`으로 미배달 메시지 읽음
- 처리 끝나면 `XACK`로 확인응답 → 이걸로 "처리 완료" 표시
- 타임아웃된 메시지는 `XAUTOCLAIM`으로 다른 워커한테 재할당 (크래시 복구용)

**과제 적용 설계 — 원문과 달리 별도 AI Worker로 확장**

이번 과제 완료조건은 "FastAPI와 AI 워커의 작업이 명확히 분리"되는 것이라, 원문처럼 같은 프로세스 안에 두지 않고 **AI Worker를 완전히 별도 프로세스(컨테이너)로 분리**해서 Streams의 producer/consumer 개념만 가져다 쓰는 구조로 설계함. Redis Streams 명령어 자체(`XADD`/`XREADGROUP`/`XACK`)는 원문과 동일하게 쓰되, consumer가 FastAPI 안의 백그라운드 태스크가 아니라 별도 AI Worker 프로세스라는 점이 다름.

**Celery 방식** (velog·nickygod, plainenglish.io 참고)

- `task.delay()` 또는 `task.apply_async()` 호출 → Redis가 브로커로 작업 큐잉
- 워커가 폴링해서 작업 가져가 실행 (이 방식은 원문에서도 워커가 별도 프로세스/컨테이너로 분리됨)
- 결과를 Redis(backend)에 저장
- `task_routes` 설정으로 작업 종류별 큐 분리 가능 (예: AI 추론 전용 큐 `ai_inference_queue` 따로 두기)

**두 방식 비교**

| | Streams (직접 구현) | Celery (+Redis) |
|---|---|---|
| 제어 수준 | 저수준, 직접 ack/재시도 관리 | 고수준, 재시도/스케줄링 내장 |
| 워커 분리 | 원문 예시는 미분리, 과제 적용 시 분리 필요 | 기본적으로 워커 프로세스 분리 |
| 학습 난이도 | Redis 명령어 직접 다뤄야 함 | 데코레이터 기반이라 쉬움 |

과제의 "FastAPI/AI Worker 분리" 요구사항만 놓고 보면, **원문 그대로의 Streams 예시보다 Celery 쪽이 구조적으로 더 잘 맞음** — 다만 Streams도 consumer를 별도 프로세스로 떼어내면 똑같이 요구사항을 만족할 수 있음.

## 6. AI Worker의 역할 `[학습·설계]`

AI Worker는 **Consumer**임. 큐에서 작업을 꺼내서 `worker/model.py`의 `predict()`를 실제로 실행하는 역할.

- FastAPI 프로세스와 완전히 분리된 별도 프로세스(또는 별도 Docker 컨테이너)로 돌아감
- 처리 끝나면 결과를 DB(`ai_analysis_results`)에 저장하고 상태를 "완료"로 갱신
- velog 자료 예시처럼, Docker Compose에 `celery_worker` 같은 별도 서비스로 띄우는 게 일반적 패턴

지금 프로젝트엔 이 역할이 따로 없고, FastAPI 프로세스 안에서 `run_in_threadpool`로 같이 처리하고 있음.

## 7. FastAPI와 AI Worker의 책임 분리 `[학습·설계]`

| | FastAPI | AI Worker |
|---|---|---|
| 성격 | I/O 바운드 | CPU(또는 GPU) 바운드 |
| 하는 일 | 요청 수신, 검증, enqueue, 상태 조회 응답 | 실제 추론 실행 |
| 확장 방법 | 요청 늘어나면 FastAPI 인스턴스 늘림 | 추론 부하 늘어나면 워커 프로세스 늘림 |

핵심 원칙: **FastAPI가 `predict()`를 직접 호출하지 않는다.** 지금 구조와 가장 큰 차이점이 여기임 — 지금은 FastAPI 서비스 레이어가 `worker.model.predict`를 직접 import해서 호출하고 있음.

## 8. 작업 상태 관리와 task_id `[EDA 적용 후 제안 설계]`

지금 API엔 task_id도, 상태 조회 엔드포인트도 없음(즉시 동기 응답이라 필요가 없었음). 아래는 EDA 적용 시 새로 추가해야 하는 개념.

**Celery 기준 상태 흐름** (plainenglish.io 참고)

```
PENDING → STARTED → SUCCESS
                   → RETRY → (재시도) → SUCCESS 또는 FAILURE
```

작업 등록 시 고유 `task_id` 발급받고, 이걸로 나중에 상태 조회함. 아래는 Celery에서 일반적으로 사용하는 패턴을 설명한 **개념 예시 코드**이고, 이 프로젝트에 실제 구현된 코드는 아님:

```python
result = predict_task.delay(record_id)
print(result.id)      # task_id
print(result.state)   # PENDING, SUCCESS 등
print(result.result)  # 완료됐으면 실제 결과
```

**주의할 점(Gotcha)**: result backend(Redis 등)를 설정 안 하면 상태 추적 자체가 안 됨. 그래서 Redis를 브로커뿐 아니라 backend로도 같이 써야 함.

우리 프로젝트에 적용한다면, 클라이언트가 `GET /predictions/{record_id}/status` 같은(신규 추가 필요) API로 폴링해서 "처리중/완료/실패"를 확인하는 방식이 됨.

## 9. 실패 처리와 재시도 `[EDA 적용 후 제안 설계]`

지금은 추론 실패 시 그 자리에서 예외를 던지고 끝(재시도 없음). 아래는 EDA 적용 시 도입할 재시도 메커니즘.

**Streams 방식**: 워커가 처리 중 죽으면 `XACK`을 못 보냄 → 메시지가 "미확인" 상태로 남음 → `XAUTOCLAIM`(min_idle_time 설정)으로 다른 워커가 가져가서 재처리.

**Celery 방식** (plainenglish.io 참고, 아래는 **개념 설명용 예시 코드**이고 실제 구현된 코드는 아님):

```python
@celery_app.task(bind=True, max_retries=3, default_retry_delay=60)
def predict_task(self, record_id):
    try:
        # 추론 로직
        pass
    except Exception as exc:
        raise self.retry(exc=exc)
```

- `bind=True`: task 자기 자신(`self`)에 접근 가능하게 함
- `max_retries=3`: 최대 3번까지 재시도
- `default_retry_delay=60`: 실패 시 60초 기다렸다가 재시도
- `soft_time_limit`도 걸어서, 너무 오래 걸리는 추론은 타임아웃 처리 가능 (`SoftTimeLimitExceeded` 예외로 정리 작업 후 종료)

우리 프로젝트 적용 관점: 모델 로딩 실패, 이미지 파일 깨짐 같은 상황에서 이 패턴으로 재시도하거나, 재시도 다 실패하면 상태를 FAILED로 기록.

## 10. 중복 작업 방지와 멱등성 `[학습·설계]`

**왜 필요한지**: 메시지 큐는 기본적으로 "at-least-once"(최소 한 번) 전달을 보장함 — 즉 같은 이벤트가 두 번 이상 전달될 수 있음. 워커가 처리 도중 죽거나 네트워크가 지연되면, 같은 메시지가 다른 워커한테 다시 전달되는 상황이 근본적으로 발생할 수 있다고 함(검색 자료 참고).

**Consumer group만으로는 부족함** — 정정 필요한 부분

Redis Streams의 consumer group은 "지금 이 순간 이 메시지를 어느 한 워커에게만 전달"하는 정도의 보장이지, 재전달(redelivery)까지 막아주진 않음. 워커가 처리 후 `XACK`을 보내기 전에 크래시하면, 같은 메시지가 `XAUTOCLAIM`으로 다른 워커에게 다시 갈 수 있고, 그 워커가 이미 끝난 작업을 또 처리해버릴 수 있음. Celery도 마찬가지로 exactly-once(정확히 한 번)를 기본 보장하지 않음. 즉 **consumer group/워커 구조 자체는 중복을 "줄여줄" 뿐, 완전히 막아주는 장치가 아님** — 실제 방지는 아래 멱등성 처리와 DB 제약조건이 따로 필요함.

**멱등성(Idempotency)이란**: 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 똑같은 성질. "잔액을 1000원으로 설정"은 멱등이지만, "잔액에 1000원 추가"는 멱등이 아님(두 번 하면 2000원 늘어남).

**어떻게 막을지**

- 멱등성 키로 `record_id + ai_model` 조합을 작업 식별자로 사용 — 워커가 작업을 시작하기 전에 "이미 처리했거나 처리 중인지" 먼저 확인(Idempotent Receiver 패턴)
- DB에 UniqueConstraint(`record_id` + `ai_model` 조합)를 걸어서, 애플리케이션 로직이 실수해도 DB 레벨에서 중복 insert 자체를 막는 최후 방어선을 둠 (TODO.md의 UniqueConstraint 항목과 직결)
- 즉 "멱등성 체크(애플리케이션 레벨) + UniqueConstraint(DB 레벨)" 두 겹으로 막아야 안전함

## 11. 전체 이벤트 흐름

**현재 실제 흐름** `[실제 코드 근거]`

```
클라이언트
  ↓ POST /api/v1/medical-records/{record_id}/predictions
FastAPI
  ↓ 검증 → 캐시 조회 → (없으면) predict() 동기 실행 → DB(ai_analysis_results) 저장
  ↓ 201 Created(신규) 또는 200 OK(기존 결과 재사용)로 즉시 응답
클라이언트
  ↓ 응답을 그 자리에서 바로 받음 (폴링 없음)
```

**EDA 적용 후 제안 흐름** `[학습·설계]`

```
클라이언트
  ↓ POST /predict (record_id)
FastAPI (Producer)
  ↓ 검증 후 Redis에 enqueue
  ↓ 즉시 202 Accepted + task_id 응답
Redis (Queue/Broker)
  ↓ AI Worker가 consume
AI Worker (Consumer, 별도 프로세스)
  ↓ worker/model.py predict() 실행
  ↓ 결과를 DB(ai_analysis_results)에 저장 + 상태 갱신
클라이언트
  ↓ GET /predictions/{task_id}/status 로 폴링 (신규 추가 필요)
  ↓ 완료되면 결과 수신
```

> (다이어그램 이미지는 과제2 완료 후 이 자리에 삽입 예정)

## 12. 우리 프로젝트에 적용할 수 있는 구조 `[설계 제안, 아직 미구현]`

- `app/apis/prediction_apis.py`의 `POST /api/v1/medical-records/{record_id}/predictions` 핸들러: 지금은 즉시 `predict()` 실행 후 `201`/`200` 응답 → **enqueue만 하고 `202`+task_id를 반환하도록 변경 제안**
- `worker/` 디렉토리를 FastAPI 프로세스에서 import해서 쓰는 게 아니라, **별도 실행 프로세스로 전환**
- `docker-compose.yml`에 `redis`, `ai-worker` 서비스 **추가 제안** (지금은 `api` + `db`만 있음)
- `ai_analysis_results` 테이블에 진행 상태(status) 컬럼 추가 여지 있음
- 멱등성 키(`record_id` + `ai_model`) 기반 중복 방지 로직 + DB UniqueConstraint를 Worker/DB 양쪽에 추가

**이 섹션은 전부 설계 제안임. Redis/Celery/AI Worker 관련 코드는 이 프로젝트에 아직 하나도 구현되지 않았고, 이번 day9 범위는 문서화까지임. 실제 구현은 추후 별도 과제로 진행 예정.**

## 13. 추가로 학습한 Celery 고급 기능 `[학습·설계, 신규 섹션]`

과제 범위(동시성 해결)에 직접 쓰이진 않지만, 참고자료(plainenglish.io) 읽으면서 같이 알게 된 내용:

- **Celery Beat**: `crontab` 문법으로 주기적 작업 예약 가능 (예: 5분마다 실행)
- **Task Chain / Group**: `|`로 작업을 순차 연결(chain)하거나, `group()`으로 여러 작업을 병렬 실행 후 결과 취합 가능
- **모니터링**: Flower(`localhost:5555`)로 task 상태를 웹 대시보드에서 실시간 확인 가능, Prometheus 연동도 됨

나중에 워커가 여러 개로 늘어나거나 스케줄링이 필요해지면 참고할 개념으로 기록해둠.
